# Mobile measurement

1. Inventory the installed build, package/bundle ID, environment and SDK versions. Match them to the Firebase project, app stream, Google Ads customer, Meta app and dataset, and AdMob app. Keep staging outside production attribution. Audit existing permission defaults and actual SDK startup, including old installed versions.
2. Initialize Firebase Analytics on the correct app and enforce approved collection and consent before eligible delivery. With applicable platform rules, account for ATT, regional CMP/UMP and changes while signed in or after logout. Keep recommendations, usage analytics, ad measurement and personalization as clearly defined purposes. An owner preference to enable personalization does not supply an individual user's choice.
3. Preserve automatic SDK events. Map new signup, returning login, verified lifecycle milestones, meaningful views, checkout and approved purchases. Use a bounded property such as `account_role = buyer | seller` when useful; clear or update it at identity changes. A canonical event can carry a role without duplicating it into separate conversion actions. Use role-specific audiences or goals only as the requested decision calls for. Review current audience retention limits, consent, policy restrictions and minimum size.
4. Where needed, link the correct Firebase/GA4 property to Google Ads and import eligible key events from the intended app stream. Inspect both ends before linking. Audit conversion category, count/value and per-campaign action selection. Native attribution and store-install measurement depend on actual platform and campaign eligibility. A GA4 import has different implementation and evidence from a direct Google Ads upload.
5. Install or configure Meta App Events SDK only within the authorized scope. Confirm exactly which automatic and explicit events the SDK emits. App CAPI is a distinct native route with its own source schema, device metadata and permissions. For a migration, route events safely across old and current app builds; verify provider-supported deduplication before sending an equivalent event over both transports. Pixel is used for applicable web content. Keep registration and app activation distinct. Follow the [signed-in matching and account-switch test](conversion-routes.md#signed-in-user-matching-on-every-eligible-event).
6. For AdMob, link the correct Firebase/Analytics app and verify supported **impression-level** revenue. Keep a single monetary source and preserve micros-to-currency conversion, currency, platform, format and ad-unit context when used. UMP readiness to request ads and eligibility for personalized delivery are distinct. Use test ads during QA. Time interstitials at suitable transitions and judge retention and completed sessions alongside yield.
7. Verify install/update, fresh grant/deny, later revocation, account switch, process restart and offline-to-online behavior. Check Firebase DebugView and reports, Ads import processing and campaign attribution, Meta Test Events or recorded diagnostics, and isolated AdMob impression revenue. For acquisition analysis compare matched-country cohort LTV, retention and CPI. Use real revenue for value optimization when supported and sufficient.

## Server-confirmed app purchases

Select one route for a purchase confirmed after the native checkout. A Firebase/GA4 Measurement Protocol route uses the correct Firebase app ID and eligible app instance ID from the originating client, with credentials kept server-side. A verified buyer-app callback can be another route if it reaches the client and reliably handles duplicate display/reopen events. Do not mirror an app purchase into a web stream to fill reporting gaps. Preserve the genuine approval/outcome time separately from the acquisition/session time. Verify current ingestion and session-join limits. A delayed approval can legitimately have weaker attribution.
