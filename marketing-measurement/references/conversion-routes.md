# Conversion routes and matching

## Google Ads

| Need | Route | What to verify |
| --- | --- | --- |
| Optimize for suitable GA4 or Firebase events | Link property and import eligible events | Correct source stream, Ads action and campaign goal, one intended conversion per outcome, reporting delay and attribution |
| Improve matching for allowed website form or purchase signals | Google tag or GTM with enhanced conversions for web | Eligible first-party user-provided data mapped via the supported field, consent and diagnostics. Check supported server-side options for the particular action. |
| Deliver trusted CRM and offline outcomes or eligible additional server-side events | Google Data Manager API or supported Data Manager integration | Correct Ads customer/action and ingestion source, schema, consent, click ID and eligible first-party match fields, transaction ID, time zone and status |
| Centralize tagging infrastructure | Server-side GTM where justified | Container, requests/clients, downstream tags, consent forwarding, transport/retries and end-to-end behavior |

The website or CRM backend can call supported provider APIs directly. Provisioning a server GTM container is optional. Verify the Google Ads conversion action and ingestion source before using a direct route, especially for online events, lead feedback and multi-source actions. Keep provider credentials on the backend.

For new Google offline conversion and enhanced-conversions-for-leads integrations, follow the current migration and Data Manager documentation. Legacy Google Ads API paths have eligibility restrictions. Record the exact endpoint and action type instead of treating all server-side Google tracking as one system.

Check auto-tagging and that each eligible lead carries the original genuine click ID where available. For Data Manager batches with multiple destinations, set explicit destinationReferences per event or split by destination. Bind consent per event where choices differ. Keep a request record-index to event/destination mapping for partial-result reconciliation. Use provider-supported matching fields and actual conversion dates/amounts. Normalize each contact for its destination before hashing. For example, check the current Google E.164 requirement and Meta country-code/digit formatting separately. Avoid reusing one provider contact hash as another provider payload. Record upload/retrieval status separately from attributed reporting and observe the applicable time window. For accepted Data Manager requests, store the returned request_id and retrieve per-destination status. Inspect SUCCESS, FAILED or PARTIAL_SUCCESS, warnings and affected record indices. Retry only eligible corrected records, not items that succeeded. Use validateOnly as a request validation check where supported; it does not produce processed-event evidence. Check the route's upload deadline, the conversion action's attribution window and reporting lag separately. Record expired outcomes and preserve their actual time. [Data Manager routing](https://developers.google.com/data-manager/api/devguides/events/google-ads/offline/send-events) · [Data Manager diagnostics](https://developers.google.com/data-manager/api/devguides/diagnostics) Keep transaction identity and value stable across permitted retries. For dual imports and tags, distinguish duplicate delivery, duplicate bidding and duplicate totals in reporting. Secondary actions can still appear in All conversions and can be used for bidding when included in a campaign custom goal. Segment by conversion action, inspect account-default and custom goals, and verify one outcome in the intended bidding path. Disable the obsolete sender or import only after a verified cutover, preserving useful history. [Primary and Secondary actions](https://support.google.com/google-ads/answer/10995103)

## Offer a Google Ads route choice

After identifying the surface and objective, show the eligible route options and recommend one. If the user already chose an eligible route, confirm that choice and continue.

| Option | Best fit | Google Ads reporting freshness |
| --- | --- | --- |
| Direct Google Ads conversion tag, deployed through web GTM or a Google tag | Owned website with a reliable browser conversion signal and a need for quicker Ads reporting | Google's comparison lists about **3 hours for last-click** and **15 hours for other models**. GTM can dispatch at the event trigger. Dispatch time does not tell you when the report or bidding will use the conversion. |
| GA4 key event or Firebase event imported into Google Ads | Existing Analytics event contract, especially eligible native app conversions, or a funnel where a shared event definition matters | Google's comparison lists **12 hours for last-click** and **24 hours for other models**. The import guide says data can take up to **24 hours** to appear in Ads. GA4's own reports can take **24–48 hours** to process and stabilize. These describe different stages. |
| Eligible server-side Google Ads route | Server-verified orders, CRM-qualified leads, or a deliberate supported server-side tag implementation | Check the chosen Google Ads or Data Manager route, provider processing, validation and attribution. Web-tag and GA4-import timings do not establish a server upload schedule. |

Offer direct website Ads tracking for quicker reporting when it fits, and keep GA4 available for analytics if requested. Offer Firebase/GA4 import for supported app events. Confirm **one intended bidding action** per business outcome per campaign and check any custom goals. If there is a reason to run both for comparison, keep the observation action out of bidding goals and report by action. A planning estimate such as **1–2 hours** can be recorded as a measured project observation when evidence supports it. Avoid promising that timeframe or a fixed Smart Bidding processing time.

## Meta by conversion source

- **Website:** Link the correct website pixel/dataset. For a simultaneous browser and server copy, share the exact event name and event identity. Browser Pixel uses `eventID`; CAPI uses `event_id`. For a server-only confirmed outcome, prefer one authoritative sender unless a legitimate buyer-side copy is designed and validated.
- **Native app:** Verify the app/dataset and use the app-specific SDK/CAPI schema and policy. Do not copy website identifiers into app events just because a form has similarly named fields.
- **Business Messaging:** Use the actual linked messaging account/channel and supported conversion events. Bind the original referral `ctwa_clid` to its conversation when eligible. For a qualified lead sent after a verified CRM transition, check the current schema for `action_source=business_messaging`, `messaging_channel=whatsapp`, the linked business messaging account/dataset, event fields and supported event name, such as `QualifiedLead` where eligible. If the click ID is absent, check current fallback requirements and omit the event if no supported eligible match path exists.
- **Offline/CRM:** Choose the real source of the action, such as phone or in-store, and the supported API. Under authorized setup, check dataset-to-ad-account tracking assignment and available auto-tracking settings. A CRM sending events does not change their original source. Keep separate identities for different outcomes and one Purchase per sale.

## Signed-in user matching on every eligible event

For a consented signed-in user, include their available, verified and permitted matching fields with **each eligible Meta event** on web or app. Apply one shared eligibility and matching policy to the Meta routes rather than enriching only registration, login or Purchase. The event still carries its real name, source, time and relevant activity fields. Eligible ViewContent, cart, checkout, confirmed lead and purchase events use the same identity-selection rule. Send events selected in the event registry.

- Resolve identity from the authenticated session or the authoritative record of the original outcome. Avoid relying on an email, phone or user ID submitted as an ordinary event parameter. For staff-approved orders the identity is the original customer. A guest may use their own eligible journey context, and must never inherit a previous account's matching data.
- Include verified email and phone when available, permitted and supported, plus the approved stable external ID wherever the route supports it. For direct CAPI, normalize and SHA-256 hash contact fields per Meta's format and put them in the supported `user_data` fields. Keep safe activity attributes such as product IDs, account role, value and currency in the appropriate event fields. Never put contacts or hashes in `custom_data`, GA4 event parameters, public dataLayer or logs. For Pixel or App Events SDK use their documented advanced matching interface and verify its hashing behavior; avoid double hashing.
- Apply the actual advertising permission and source restrictions on each dispatch. After logout, account switch, or withdrawal, clear or replace SDK and browser matching context through the supported integration. Keep delayed jobs tied to their original user/outcome and recheck that user's current permission. Do not attach a new user's identity to an old event or replay a previously denied event after consent.
- Test two synthetic accounts with distinct identities. On web and app, view content and complete eligible actions as account A, sign out, switch to B and revoke. Confirm correct hashed matching fields accompany events for A and B, no A-to-B leakage, no identified guest traffic and no dispatch where consent denies it. Use field-presence and isolated test evidence rather than logging direct identifiers. Include offline buffering, switching A to B before reconnecting, app restart and SDK automatic events. Check the installed SDK version for whether user ID and matching fields bind at event creation or flush. Clear both SDK user ID and matching data where supported. If event/account isolation cannot be verified, leave SDK identity enrichment off for that route and use an eligible event-bound app CAPI path only when appropriate.

### Verified email and mobile

Treat verified first-party email and mobile as priority matching fields when they serve the business purpose, the user has given the required permission, and the destination supports them. Collect them through account verification, an eligible form, checkout or a properly scoped CRM. Preserve provenance, including whether each field is self-reported or verified. Avoid making irrelevant fields mandatory solely for tracking. Never use scraped, purchased, fabricated, borrowed or stale contact data. Match the original customer even when staff approves an order later.

Check field coverage among eligible, consented events and report why fields are missing. For Meta, apply the signed-in matching rule across eligible events. For Google, use the action's supported Enhanced Conversions, Data Manager or authorised GA4 user-provided data channel. Normalize for the exact destination, use approved hashing and verify the actual delivery path. Keep contact fields and hashes out of general event parameters, public dataLayer, URLs, Clarity captures and logs. Treat hashes as personal data and apply approved retention and access controls.

### Stable external ID

Include `external_id` in the supported Meta identity field on every eligible signed-in event when permission and the selected route allow it. Use a stable, opaque first-party account identifier scoped to the business and environment. Two devices using the same eligible account should use the same ID for the approved integration. Keep its representation consistent across linked Pixel, SDK and CAPI routes where supported. Follow the destination format, such as SHA-256 where recommended or required, and verify that the SDK or partner does not hash an already-hashed value again.

| Identifier | Meaning | Scope |
| --- | --- | --- |
| `external_id` | Who performed the action | Stable across that permitted account's eligible events. A guest uses separately eligible browser or journey context, without inheriting any signed-in account ID. |
| `event_id` | Which event occurred | Stable for paired browser/server copies and permitted retries. A different event gets a distinct ID. |
| `transaction_id` or `order_id` | Which sale occurred | Stable for the same sale or adjustment linkage, even if the same account buys many times. |

Keep email, phone, payment details, device fingerprint and ephemeral session IDs out of the source identifier. If a route cannot carry this identity, document the reason and the supported alternative. Test identifier stability across sessions and separation across accounts, business environments, and guest sessions.

## Website CAPI matching rules

| Field | What to send when permitted and supported |
| --- | --- |
| `em`, `ph` | Actual eligible customer email and phone, normalized and SHA-256 hashed according to Meta’s exact rules. Use verified contact where the project requires it. |
| `fn`, `ln`, `ct`, `st`, `zp`, `country` | Permitted, reliable values normalized and hashed as documented. Omit unavailable or unnecessary fields. Review automatic website matching separately from automatic event generation. |
| `external_id` | Required checklist field for eligible signed-in activity. Use the stable approved identity and consistent format described in this guide. |
| `fbp`, `fbc` | Genuine browser/click-derived values, un-hashed. Use a valid captured click to construct `fbc` only per Meta's documented method. Leave absent for visits without an eligible click or cookie. |
| `client_ip_address`, `client_user_agent` | Original user request values where allowed and applicable, un-hashed. Apply a trusted proxy configuration, and never substitute approval operator, worker or hosting IP/UA. Check required field behavior before sending events without original context. |
| Event context | `event_name`, genuine `event_time`, `event_id`, true `action_source`, sanitized `event_source_url` where applicable, and supported `custom_data` such as item IDs and value/currency. |

For automatic advanced matching, inspect the master toggle and each captured field. Confirm consent, approved scope, and behavior on client forms. Leave automatic phone extraction disabled when verified-only phone is the contract, and use the eligible verified server route. Only enable sensitive fields when explicitly needed and supported. Check missing fields by eligible source cohort. Organic traffic often has no eligible click ID. Match quality can improve with more accurate fields on eligible events; score improvements and increased attribution require evidence. Hashing and automatic matching do not establish permission. Review consent at event generation and dispatch, preserve stable job identifiers, never backfill activity from a denied period solely because a later grant exists, and do not send a duplicate Purchase to fill reporting gaps.
